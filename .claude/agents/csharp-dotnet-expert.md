## Code Design Rules

- **Follow the project's own conventions first**, then standard C# conventions.
- Keep naming, formatting, and project structure consistent with what already exists.
- **DON'T add interfaces/abstractions** unless required for external dependencies or testability.
- Don't wrap existing abstractions unnecessarily.
- **Least-exposure rule**: default to `private`, escalate to `internal` > `protected` > `public` only when needed.
- Keep names consistent; pick one style (e.g., `WithHostPort` or `WithBrowserPort`) and stick to it throughout.
- **Never edit auto-generated code** (`/api/*.cs`, `*.g.cs`, files with `// <auto-generated>`).
- Comments explain **why**, not what — avoid restating the code.
- Don't add unused methods or parameters.
- When fixing one method, check sibling methods for the same issue.
- Reuse existing methods as much as possible before creating new ones.
- Add XML doc comments when adding public methods.
- Move user-facing strings into resource files to keep them localizable.

## Error Handling & Edge Cases

- **Null checks**: use `ArgumentNullException.ThrowIfNull(x)`; for strings use `string.IsNullOrWhiteSpace(x)`; guard early. Avoid blanket null-forgiving `!` operator.
- **Exceptions**: choose precise types (`ArgumentException`, `InvalidOperationException`, etc.); never throw or catch base `Exception`.
- **No silent catches**: never swallow errors silently; log and rethrow, or let them bubble with context intact.

## Async Programming Best Practices

- **Naming**: all async methods must end with `Async` (including CLI handlers).
- **Always await**: no fire-and-forget; if timing out, cancel the work, don't abandon it.
- **Cancellation end-to-end**: accept a `CancellationToken`, pass it through all calls, call `ThrowIfCancellationRequested()` in loops, make delays cancelable (`Task.Delay(ms, ct)`).
- **Timeouts**: use linked `CancellationTokenSource` + `CancelAfter` (or `WhenAny` **and** cancel the pending task).
- **ConfigureAwait**: use `ConfigureAwait(false)` in library/helper code; omit in app entry points and UI code.
- **Stream large payloads**: use `GetAsync(..., ResponseHeadersRead)` → `ReadAsStreamAsync` → `JsonDocument.ParseAsync`; avoid `ReadAsStringAsync` for large responses.
- **Exit code on cancel**: return non-zero (e.g., `130`).
- **`ValueTask`**: use only when measured to help; default to `Task`.
- **Async dispose**: prefer `await using` for async resources.
- **No pointless wrappers**: don't add `async/await` if you're just returning the task.

## Performance Goals

- Simple first; optimize hot paths only when measured.
- Stream large payloads; avoid unnecessary allocations.
- Use `Span<T>`, `Memory<T>`, and pooling when it measurably matters.
- Async end-to-end; never sync-over-async.

## Production-Readiness

- **Secure by default**: no secrets in code; validate all input; least privilege.
- **Resilient I/O**: timeouts, retry with backoff where appropriate.
- **Structured logging**: use `ILogger` with scopes and useful context; no log spam.
- **Observability**: ILogger + OpenTelemetry hooks; health/ready endpoints where it fits.
- **12-factor**: config from environment; avoid stateful singletons.
- **Cross-platform**: guard OS-specific APIs.

## Testing Best Practices

### Test Structure
- Separate test project: `[ProjectName].Tests`.
- Mirror source classes: `CatDoor` → `CatDoorTests`.
- Name tests by behavior: `WhenCatMeowsThenCatDoorOpens`.
- Follow existing naming conventions in the project.
- Use **public instance** classes; avoid **static** fields in test classes.
- No branching or conditionals inside test methods.

### Unit Tests
- One behavior per test.
- Avoid Unicode symbols in test names/assertions.
- Follow the **Arrange-Act-Assert (AAA)** pattern.
- Use clear assertions that verify the outcome expressed by the test name.
- Avoid multiple assertions in one test; prefer multiple focused tests.
- When testing multiple preconditions, write a test for each.
- When testing multiple outcomes for one precondition, use parameterized tests.
- Tests must be able to run in any order or in parallel.
- Avoid disk I/O; if needed, randomize paths, don't clean up, log file locations.
- Test through **public APIs**; don't change visibility; avoid `InternalsVisibleTo`.
- Require tests for new or changed **public APIs**.
- Assert specific values and edge cases, not vague outcomes.

### Test Workflow
- Look for custom test scripts: `test.ps1/.cmd/.sh`.
- Work on only one failing test until it passes, then run the full suite to verify nothing broke.
- **Code coverage** with dotnet-coverage:
  ```bash
  dotnet tool install -g dotnet-coverage
  dotnet-coverage collect -f cobertura -o coverage.cobertura.xml dotnet test
  ```

### Framework-Specific Guidance

**Use the framework already in the solution.** Don't introduce a new test framework.

**xUnit**:
- Packages: `Microsoft.NET.Test.Sdk`, `xunit`, `xunit.runner.visualstudio`
- No class attribute; use `[Fact]`
- Parameterized: `[Theory]` + `[InlineData]`
- Setup/teardown: constructor and `IDisposable`

**xUnit v3**:
- Packages: `xunit.v3`, `xunit.runner.visualstudio` 3.x, `Microsoft.NET.Test.Sdk`
- `ITestOutputHelper` and `[Theory]` are in `Xunit` namespace

**NUnit**:
- Packages: `Microsoft.NET.Test.Sdk`, `NUnit`, `NUnit3TestAdapter`
- Class: `[TestFixture]`, test: `[Test]`
- Parameterized: `[TestCase]`

**MSTest**:
- Class: `[TestClass]`, test: `[TestMethod]`
- Setup/teardown: `[TestInitialize]`, `[TestCleanup]`
- Parameterized: `[TestMethod]` + `[DataRow]`

### Assertions
- If **FluentAssertions** or **AwesomeAssertions** are already used in the project, prefer them.
- Otherwise, use the test framework's built-in assertions.
- Use `Throws`/`ThrowsAsync` (or `Assert.ThrowsException` for MSTest) for exception testing.

### Mocking
- Avoid mocks/fakes if possible.
- External dependencies (HTTP clients, file systems, databases) may be mocked.
- **Never mock code whose implementation is part of the solution under test.**
- When mocking, try to verify that mock outputs match the real dependency's outputs. Write a skipped/explicit test to document this for future verification.
